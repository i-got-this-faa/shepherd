# 06 — Configuration pipeline

How administrator intent becomes per-platform, signed, deployable artifacts.

## Config repository `[impl]`

The control plane owns one git repository (bare, at `config_repo_path`) that is
the canonical store of desired state. It is a Nix flake:

```text
flake.nix                      # aggregator; inputs: nixpkgs (pinned), shepherd (this monorepo's lib), nix-darwin
flake.lock
profiles/<profile-slug>/
  generated.json               # GUI model, written ONLY by the control plane [CFG-02]
  custom/*.nix                 # administrator custom modules (advanced editor) [CFG-01]
  profile.nix                  # thin aggregator: imports shepherd modules + generated + custom (generated by CP, not edited)
hosts/<machine-id>/
  hardware.nix                 # NixOS hardware config captured at enrollment
  host.json                    # machine facts used during evaluation (hostname, platform, edition, capabilities)
```

Outputs the aggregator exposes, per machine assigned to a profile:

- `nixosConfigurations.<machine-id>` for NixOS machines.
- `darwinConfigurations.<machine-id>` for macOS machines.
- `shepherdWindows.<machine-id>` → attrset evaluated to the Windows resource list.
- `shepherdObservations.<machine-id>` → observation resources for NixOS/Darwin drift ([12](12-nixos-backend.md)).

Per-machine outputs are required because NixOS hardware config and Windows
edition capabilities differ per machine. Evaluation of a *profile* for review
uses a representative machine per platform (or a synthetic host for previews
when none is enrolled).

Every saved change is a commit by the control plane with author metadata
(`Shepherd <admin:alice>`, `Shepherd <agent-draft:session-id>`). Drafts live on
branches `drafts/<draft-id>`; approval merges (fast-forward) into `main`.
A **configuration identity** = `main` commit sha + profile id + platform [CFG-04].

## GUI model (`generated.json`)

Versioned JSON (`guiModelVersion: 1`) with sections that map 1:1 to
`shepherd.*` options in [07](07-nix-modules.md):

```json
{
  "guiModelVersion": 1,
  "shared": {
    "packages": [ { "id": "firefox", "windows": { "winget": "Mozilla.Firefox" }, "nixos": { "attr": "firefox" }, "darwin": { "attr": "firefox" }, "version": "pinned-by-catalog" } ],
    "environment": { "variables": { "JAVA_HOME": { "value": "...", "platforms": ["windows"] } }, "path": { "append": [ "C:\\Tools\\bin" ] } },
    "services": [ { "name": "sshd", "state": "running", "startup": "automatic", "platforms": ["nixos"] } ],
    "firewall": { "rules": [ { "name": "Allow SSH", "direction": "in", "action": "allow", "protocol": "tcp", "ports": [22] } ] },
    "accounts": [ { "name": "labadmin", "groups": ["Administrators"], "ensure": "present" } ],
    "network": { "dns": ["10.0.0.1"], "proxy": null }
  },
  "windows": { "registry": [ ... ], "policies": [ ... ], "tasks": [ ... ], "updates": { ... } },
  "nixos": { "extra": { ... } },
  "darwin": { "defaults": { ... }, "mdmProfiles": [ ... ] }
}
```

Rules:

1. The GUI edits only `generated.json` [CFG-02]. Rendering never rewrites
   `custom/*.nix`.
2. `generated.json` is imported via `builtins.fromJSON` inside a fixed module
   (`shepherd.lib.fromGuiModel`) that sets options at normal priority. Custom
   modules are imported alongside. Two definitions of a unique option produce
   the standard Nix "conflicting definition values" error [CFG-05]; admins
   resolve by editing one side or using `lib.mkForce` in custom code.
3. Secrets are never put in `generated.json` (account passwords are out of V1
   scope per SRS Platform limits; accounts are created without passwords or
   with "must set on first login" where supported).

## Package catalog

`packages/configuration/catalog/` holds a curated, versioned catalog mapping a
Shepherd package id to per-platform sources (winget id + pinned version,
nixpkgs attr, nix-darwin attr/homebrew cask if used). The GUI picks from it;
the advanced editor can bypass it. Upgrades happen only by changing the pinned
version or bumping `flake.lock` through an approved draft [DEP-02].

## Evaluation

Evaluation runs in the build worker ([08](08-build-and-artifacts.md)) in a sandbox:

| Platform | Command (conceptual) | Output |
|---|---|---|
| Windows | `nix eval --json .#shepherdWindows.<host>` | Resource list JSON → plan compiler |
| NixOS | `nix eval .#nixosConfigurations.<host>.config.system.build.toplevel.drvPath` then build on approval | drv path; on build: store path |
| Darwin | same for `darwinConfigurations` | drv path / store path |
| Observations | `nix eval --json .#shepherdObservations.<host>` | Observation resources |

Errors are captured with file/line (parse `error:` blocks from `nix` stderr,
including `at /…/profiles/x/custom/foo.nix:12:3`) and returned as
`evaluations.error_location` so the GUI can point at the GUI field or custom
file [CFG-05, DEM-04]. Timeouts: 120 s eval, configurable.

## Plan compiler (Windows)

`apps/control-plane/internal/configuration/compile/windows.go`:

1. Input: evaluated resource list + `host.json` capabilities.
2. Validate each resource against the provider schema; unknown resource → error.
3. Capability filter: resources requiring an unsupported capability move to
   `omitted[]` with reason [CFG-06]. Example: `windows.policy` on Home when the
   admin chose `requirePolicyEngine = true`; registry-backed fallback only if
   the option allows it and the reason is recorded.
4. Assign `class`, `reversible`, `destructive` from the provider table.
5. Topologically sort with `dependsOn`, rejecting cycles/unknown ids.
6. Produce the plan template stored in `generations.signed_plan_template`;
   per-machine finalization at dispatch adds `machineId`, `planId`, times,
   `recovery.lastWorkingGenerationId`, then signs [DEP-01].

## Diffs [CFG-04, CFG-07]

Three diff kinds, all shown in the console:

1. **Source diff**: git diff between base revision and draft (GUI model shown
   as a structured field diff, custom modules as text diff).
2. **Plan diff** per platform: resource-level added/changed/removed between
   current generation's plan and the draft's plan preview, with `destructive`
   and `owner` flags. NixOS/Darwin: closure diff via `nix store diff-closures`
   (package version changes) plus observation resource diff.
3. **Machine transition preview** for profile switches [PRF-04]: for a given
   machine, current active generation vs the new effective profile's generation.

A diff is never treated as convergence evidence (convergence comes only from
node reports) [CFG-07].

## Capability coverage report

For each draft evaluation and platform: count of resources planned vs omitted
with reasons. The console shows "N settings not enforceable on Windows Home"
etc. Agents can propose equivalents as new drafts [CFG-06, DEM-05].

## Acceptance

- Unit: GUI model → rendered profile tree is deterministic (golden files).
- Unit: custom module untouched after 100 random GUI edits (property test).
- Integration (needs Nix): conflicting definitions return a located error; a
  valid profile evaluates for Windows, NixOS, Darwin synthetic hosts.
- Compiler: capability filtering moves policy resources to `omitted` on a Home
  host fixture and keeps them on a Pro fixture.
- DEM-04 passes: invalid custom Nix blocks publication; current target unchanged.
