# winget Surface

winget (Windows Package Manager, shipped as App Installer) installs, upgrades,
and removes packages. The mapper uses winget as the package provider and does
not reimplement package reconciliation.

## What the mapper maps

| Plan intent | winget operation | Notes |
|---|---|---|
| A package must be installed at a version | `winget install --id <id> --exact --version <v> --silent` | Machine scope for fleet software |
| A package must be the latest | `winget upgrade --id <id> --exact --silent` | Pin or latest are separate resource fields |
| A package must not be installed | `winget uninstall --id <id> --exact --silent` | Records the exit code |
| Inventory installed packages | `winget list` | Supplement to the registry uninstall keys |
| Export a machine manifest | `winget export` | Used to bootstrap a new machine from a reference one |
| Test declared state without change | `winget configure test` | Built-in drift check, see below |
| Apply a declared document | `winget configure` | DSC v3 YAML |

## Declarative mode: winget configure

`winget configure` applies a YAML document of Desired State Configuration
resources. It needs winget 1.6.2631 or later. Properties the mapper needs:

1. Idempotency. `winget configure test` reports which resources already
   match without changing the machine.
2. Dependencies. The `dependsOn` field ties resources to assertions;
   execution order is otherwise not sequential, and some resources run in
   parallel.
3. A JSON schema for the YAML, so the server can validate generated
   documents before shipping them.

Organizations can disable the feature through the
`EnableWindowsPackageManagerConfiguration` Group Policy objects, which is
also the switch the mapper uses to keep end users from running their own
configurations on a managed machine.

The mapper keeps plan authorship in nix and can hand the package section to
`winget configure` as a generated document. Decision: the first
implementation drives the plain winget verbs per package because each
package is one journalable operation. `winget configure` is the second
step, when the mapper needs multi-resource packages.

## Programmatic path

Microsoft states in the official troubleshooting guide that **the winget CLI
is not supported in the system context**: an MSIX package cannot be
registered for `NT AUTHORITY\SYSTEM`. The mapper agent runs as a SYSTEM
service, so shelling out to `winget.exe` is not the supported path for the
agent. Two supported options:

1. The COM API (`Microsoft.Management.Deployment`). The runtimeclass
   `PackageManager` exposes `InstallPackageAsync`, `UpgradePackageAsync`,
   `UninstallPackageAsync`, `DownloadPackageAsync`, and catalog queries
   through `FindPackages`, with options objects (`InstallOptions`,
   `UninstallOptions`, `DownloadOptions`) that carry scope, silent mode,
   agreement acceptance, and architecture filters. When running as SYSTEM,
   load the deployment DLL in-process (the same switch
   `Microsoft.WinGet.Client` makes with `UsesInProcWinget`); from an
   elevated admin context, the out-of-proc server
   `WindowsPackageManagerServer.exe` works. Objects activate through
   per-class CLSIDs via `CoCreateInstance`, the calling thread must be STA,
   and results carry `ExtendedErrorCode` (the `0x8A15xxxx` HRESULTs) and
   `InstallerErrorCode` (the raw installer exit code). The MIT-licensed
   `Microsoft.WindowsPackageManager.ComInterop` NuGet package ships the
   winmd, the CsWinRT projection, and activation shims. COM callers can
   also set `BypassIsStoreClientBlockedPolicyCheck`, a capability the CLI
   does not have.
2. The `Microsoft.WinGet.Client` PowerShell module, which handles the
   SYSTEM in-process switch itself.

The CLI stays useful for interactive diagnostics and for this document
set's probe suites, which run from an elevated admin context where the CLI
is supported. Decision: the mapper's package provider targets the COM API
in the SYSTEM service context; the CLI verbs remain the human and test
path.

## Exit codes

winget documents a full exit-code catalog, generated by
`winget error --output <file>`; `winget error <code>` decodes a code
locally. The codes the agent will see most:

| Code | Meaning | Agent action |
|---|---|---|
| `0x8A150014` | No packages found | Fix the query; use exact id |
| `0x8A15002B` | No applicable update (already current) | Treat as `unchanged`, not failed |
| `0x8A150010` | No applicable installer for OS, arch, or scope | Adjust scope; report `unsupported` if machine scope is impossible |
| `0x8A150101` / `0x8A150103` | Package in use / file in use | Retry with backoff |
| `0x8A150109` / `0x8A15010A` | Reboot required to finish or to install | Set `rebootRequired` in the report |
| `0x8A15010D` / `0x8A15010E` | Already installed / downgrade refused | Treat as `unchanged`; version pin decision is the server's |
| `0x8A150041` / `0x8A150046` | Package or source agreements not accepted | A bug in the agent's flags; fix and retry |
| `0x8A150076` | Interactive authentication required | The msstore source path; the agent avoids it |
| `0x8A150011` / `0x8A150060` | Hash mismatch / archive malware scan failed | Never bypass silently; report `blocked` |

Undeclared installer exit codes arrive raw (MSI 1603, 1618, 3010 and
friends); manifests can declare `ExpectedReturnCodes` so winget maps known
ones into the `0x8A1501xx` range. The report carries the code verbatim, and
the mapper's package resource maps them through this table: non-zero is
`failed` unless the code means already-current or pending-reboot.

## Invocation rules

1. Always pass `--id <id> --exact`. A name match can install a different
   publisher's package.
2. Always pass `--accept-package-agreements --accept-source-agreements`. The
   agent runs unattended and cannot answer prompts.
3. Pass `--scope machine` for fleet software. User-scope installs escape the
   machine inventory and break on another user's session.
4. Pass `--disable-interactivity`. A package that opens a window blocks the
   agent.
5. Time-box each operation. Some installers hang on a hidden dialog. The
   journal records the timeout and the agent reports it.
6. Treat a non-zero exit code as a failed resource. winget exit codes are
   documented hex values such as `0x8A15002B` (no package found). The report
   carries the code verbatim.

## Sources and availability

1. The default sources are `winget` (community repository) and `msstore`.
   The mapper uses the `winget` source; the `msstore` source needs a
   Microsoft account context that a headless agent does not have.
2. winget is absent on Windows Server and LTSC by default and ships with App
   Installer. The agent checks availability and reports `unsupported` instead
   of failing the plan.
3. Source updates are separate from package updates. `winget source update`
   refreshes the metadata; the agent runs it before a batch of applies.

## Headless configuration

Two configuration layers matter for a fleet agent:

1. Admin settings (`winget settings --enable/--disable`): `LocalManifestFiles`,
   `BypassCertificatePinningForMicrosoftStore`, `InstallerHashOverride`,
   `LocalArchiveMalwareScanOverride`, `ProxyCommandLineOptions`, and
   `DefaultProxy`. The agent leaves them at defaults unless the fleet needs
   a proxy or local archives; the `WinGetAdminSettings` DSC resource can
   enforce them declaratively.
2. Group Policy through `DesktopAppInstaller.admx` (shipped in the winget
   repository): it can disable `winget configure` for end users, pin the
   source auto-update interval (`SourceAutoUpdateInterval` is a policy, not
   an admin setting), set a machine-wide default proxy, and lock local
   manifests. The mapper writes these through the group-policy surface.

The msstore source requires interactive authentication that a headless
agent cannot perform; the agent scopes all operations to the `winget`
source. On the COM side, `AuthenticationArguments` with
`AuthenticationMode::Silent` makes store operations fail fast instead of
prompting.

## Elevation and editions

Install, upgrade, uninstall at machine scope need elevation. Inventory reads
do not. winget works on Windows 10 1809 and later and on all editions when
App Installer is present. SKUs without the Store (Server, LTSC, Server Core)
lack winget by default; the offline install is `Add-AppxPackage` with the
App Installer `.msixbundle` plus its `VCLibs` and `UI.Xaml` dependencies.
The agent checks availability and reports `unsupported` instead of failing
the plan.

## Verify

Read-only checks that prove the surface is reachable.

```powershell
winget --version
winget source list
```

Elevated evidence from the test machine: the full lifecycle ran against
`7zip.7zip` at machine scope. The probe installed pinned version 24.08
(silent, machine scope, no prompts), upgraded it to the current version,
uninstalled it, and confirmed through the registry uninstall database that
no 7-Zip entries remained. Two details the run proved: an MSI package
registers its uninstall key under its GUID product code rather than the
package name, so the inventory of record must match on `DisplayName`; and
every winget call in an unattended context needs the agreement and
interactivity flags or it hangs on a hidden prompt.
